# 可复用方法论：窗口/外壳类异常的排查顺序

面向"某个窗口行为诡异"（自动跳转、自动关闭、重复弹出、位置被改）这一类问题。

## 原则 0：先定界，再取证，最后才动手

排查的价值不在"试了多少方案"，而在**每试一次能砍掉多大空间**。
优先级：**一分钟能砍掉一半空间的测试** > 十分钟能确认的测试 > 逐个猜。

## 步骤 1：把现象变成可判读的布尔值

不要靠肉眼观察"好像跳了"。写探针，输出三态：

- `BOUNCED`（跑到了非预期位置）
- `OK`（停在预期位置）
- `NO_WINDOW`（没抓到，需加长等待）

参考 `scripts/Test-ExplorerRedirect.ps1`。

同时确认两件事，它们决定了问题性质：

1. **句柄是否变化**：同 HWND → 导航；换 HWND → 崩溃/重建。
2. **"新建" vs "已存在"是否一致**：只在新窗口出现 → 坏状态在初始化路径上。

## 步骤 2：一分钟定界 —— 换用户账户

**这是性价比最高的一步，应该尽早做。**

```
新建本地管理员账户 → Win+L 切换 → 在干净账户里复现 → 切回
```

| 结果 | 结论 | 下一步 |
|---|---|---|
| 干净账户也复现 | 整机级：系统文件 / 驱动 / 服务 / 全局软件 | 修系统、覆盖安装、干净启动 |
| 干净账户正常 | **用户配置级** | 只在 HKCU + 用户目录里找 |

> 本案例正是被这一步救下来的：前面几十轮全部无效之后，它一次性排除了"重装系统"。

## 步骤 3：整机级排查顺序（若步骤 2 显示整机复现）

1. **服务二分**（不用重启）：`scripts/Test-ServiceBisect.ps1` —— 先全停，再二分到单个服务。
2. **驱动**：枚举运行中、且文件不在 `%SystemRoot%` 下的驱动；核对签名者。
3. **系统文件**：`DISM /Online /Cleanup-Image /RestoreHealth` → `sfc /scannow`。
4. **干净启动 / 安全模式**：区分第三方启动项与系统自身。
5. 以上都无效 → 覆盖安装（保留文件与应用的修复升级）。

## 步骤 4：用户配置级的排查顺序 —— 不要逐个猜

状态库动辄几百个值（本案例的 `HKCU\...\Explorer` 有 50+ 子键、数百个值）。
正确姿势：

1. **先试整组删除**（可删就删）。带保护/被锁的子键自然会被跳过。
2. 删之前**必须导出 `.reg` 备份**，并写清回滚命令。
3. 删除时**保留**关键映射（如 `User Shell Folders` / `Shell Folders`），否则会把用户目录指错。
4. 重启宿主进程（`explorer.exe`）后再测 —— 很多状态是进程启动时读入的，不重启看不到效果。
5. 若整组删除后仍复现，才做**二分**（恢复一半 → 测 → 再一半）。

## 常见"看起来很像但通常不是"的方向

| 方向 | 为什么容易误判 | 什么时候才值得查 |
|---|---|---|
| 第三方外壳扩展 | 症状像"被扩展接管"，且网上大量案例是扩展引起 | 扩展确实加载进了宿主进程（用模块枚举确认） |
| 自动播放 / Shell 硬件检测 | 微软官方答案就是这两条 | 症状与**插拔设备**强绑定，且服务状态可复现 |
| 驱动 | "系统级"问题常被归咎于驱动 | 有签名/版本异常，或安全模式下症状消失 |
| 恶意软件 | 一切异常都像 | 有网络/持久化/提权等**独立**迹象 |
| 清缓存（BagMRU/iconcache） | 教程最多、最无害，所以先试 | 顺手试可以，但别指望它解决导航类问题 |

## 记录方式

维护一张"假设 → 验证动作 → 结果"表（见本仓库 README 第 4 节）。
它的作用不是好看，而是**防止重复试同一件事**——本案例中有多个方案在不同阶段被重复怀疑过。

## 反面教材（本案例真实发生）

- 在"哪个值坏了"上猜了 6 轮（`LaunchTo`、`SeparateProcess`、`ShellViewReentered`、`Bags`、`NameSpace`、`TypedPaths` …）→ 全部无效，纯浪费。
- 在确认"新账户正常"之前，反复在整机层面折腾（服务、驱动、扩展）→ 方向错了。
- 整键删除失败后没有立刻改为"逐子键删除"，导致多绕一轮。

**教训：先用一分钟的测试把搜索空间砍掉一个数量级，再谈技术细节。**
